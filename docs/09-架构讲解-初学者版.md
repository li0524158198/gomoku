# 09 · 系统架构讲解（初学者版）

本文档面向**初学者**：不假设你懂围棋 AI 或网络编程，用大白话 + 图解讲清楚
这个五子棋是怎么搭起来的、每一步点击背后发生了什么。读完你就能自己改代码。

---

## 1. 先看全景：这个项目只有三个"角色"

```
┌────────────────────────── 你的浏览器 ──────────────────────────┐
│                                                                │
│   ┌─────────────┐   点击/显示   ┌──────────────────────────┐   │
│   │  UI 界面层   │ ◀──────────▶ │  游戏引擎（AI 大脑+规则）  │   │
│   │  画棋盘棋子  │               │  判断胜负 / 搜索最佳落子   │   │
│   └─────────────┘               └──────────────────────────┘   │
│         │                            │                         │
│         ▼                            ▼                         │
│   localStorage（存档）         Web Worker（AI 专用小工位）       │
└────────────────────────────────────────────────────────────────┘
                      │ 仅「在线对战」时才需要 ↓
                      ▼
           ┌──────────────────────────┐
           │   服务器（gomoku-server）  │
           │   房间 / 转发落子 / 判胜负  │
           └──────────────────────────┘
                      ▲
           另一位玩家的浏览器
```

三个角色各干一件事：

| 角色 | 一句话职责 | 在哪 |
|------|-----------|------|
| **游戏引擎** | 懂规则（谁赢了）、会下棋（算出最佳落子） | index.html 里 `__ENGINE_START__` 到 `__ENGINE_END__` 之间 |
| **UI 界面层** | 画棋盘、听点击、显示状态、存档 | index.html 引擎之后的全部代码 |
| **服务器** | 在线对战时的"裁判+邮差"：转发双方落子、判定胜负 | gomoku-server.js |

**最重要的设计决定**：引擎是纯逻辑，完全不知道"页面""网络"的存在。
所以同一份引擎代码可以同时跑在三个地方——你的浏览器（人机对弈）、
测试脚本（test-engine.mjs）、服务器（在线对战时当裁判）。
改一处，三处同时生效，永远不会出现"页面上能赢、服务器上判输"的分裂。

## 2. 你点一下棋盘，背后发生了什么？

以人机对弈为例，从点击到 AI 回手，完整的一生：

```
你点击 (7,7)
   │
   ▼
humanMove(7,7)                 ← 入口：先过安检
   │  守卫：对局结束了吗？在回放吗？轮到你吗？那个点有子吗？
   ▼
doPlace(7,7,黑)                ← 落子四件套
   │  1. 棋盘数组记下这颗子
   │  2. 播放落子动画
   │  3. 播放"嗒"音效
   │  4. 重绘画面 + 刷新面板 + 自动存档
   ▼
finishCheck()                  ← 裁判：这手棋赢了吗？
   │  沿 4 个方向数连子 ≥5 → 弹结算框、存对局记录
   │  没赢 → 继续
   ▼
scheduleAi()                   ← 该 AI 走了
   │  状态改为「AI 思考中」
   │  把当前棋局打包，发给 Web Worker（独立线程）
   ▼
┌─ Web Worker（后台埋头计算，页面不卡）─────────┐
│  chooseAiMove(棋局, 白棋, 难度, 你的画像)      │
│    1. 我能一步成五吗？→ 直接下               │
│    2. 对方能一步成五吗？→ 堵住               │
│    3. 都没有 → 搜索：假装自己下一手，         │
│       假装对手应对，一层层往下推演…           │
│  算出最佳点 (8,7)，发回主页面                 │
└───────────────────────────────────────────────┘
   ▼
onmessage 收到 (8,7)
   │  落子 → 检查胜负 → 轮到你
   ▼
状态栏：「轮到你落子，点击棋盘即可」
```

**记住这个骨架，整个项目就是它的变体**：
双人模式 = 少了 AI 那一步；在线模式 = 把"AI 计算"换成"发给服务器等对方"；
悔棋 = 从棋盘上撤回棋子并清掉胜负状态；回放 = 从空盘把记录里的落子重新摆一遍。

## 3. 游戏引擎：AI 是怎么"想"的？

### 3.1 棋盘就是一个一维数组

```js
b = new Uint8Array(225)   // 15×15 = 225 格，0=空 1=黑 2=白
```

想知道 (x, y) 处有什么：`b[y * 15 + x]`。用一维数组不用二维嵌套，遍历更快。

### 3.2 判断胜负：沿四个方向数子

落下一子后，只需要看**经过这一子的 4 条线**（横、竖、两条斜线）：
从落点向两边延伸数同色棋子，加起来 ≥5 → 赢了。
`winLine()` 还会把这条线上的棋子坐标**按顺序**返回，UI 拿它画金色连线。

> 为什么这样是"准确"的？因为它是直接数数，不依赖任何评估或记忆——
> 五子棋的胜负规则本身就只有这一条。

### 3.3 AI 怎么评估一个位置好不好？

`pointScore(x, y, c)` 回答："如果 c 色在这落一子，能形成多强的棋型？"

方法很朴素：**取所有包含这个点的 5 格窗口**（一条线上有 5 个），数窗口里
己方子几个、空格几个：

| 窗口内容 | 判定 | 分值 |
|----------|------|------|
| 5 子 | 成五 | 1000 万 |
| 4 子 + 1 空 | 活四（两头空）/ 冲四（一头堵） | 100 万 / 10 万 |
| 3 子 + 2 空 | 活三 / 眠三 | 8 万 / 1 万 |
| 2 子 + 3 空 | 活二 | 6 千 |

然后叠加**组合加成**：双活三、四三相连、双冲四——这些是几乎必胜的杀型，
额外加几十万到几百万分。分值表就是 AI 的"价值观"。

### 3.4 AI 怎么搜索：假装对弈，一层层推演

`negamax` 搜索的思路像下棋时在心里推演：

```
我下这里 → 对手最好的应对是什么？→ 我再下那里 → ……
```

- **α-β 剪枝**：推演中发现"这条路对手有妙手必破"，就放弃整条分支，
  不再浪费时间细算——这是搜索能算 12 层的秘密。
- **迭代加深**：先算 2 层，再 4 层、6 层…逐级加深。算到时间上限就用
  上一层的结果——保证"再难的局面也一定会在时限内给出答案"。
- **杀棋延伸**：推演到叶子时如果棋面上有"一步成五"的威胁，不急着打分，
  继续往下算几层——防止漏掉连续冲四的杀招。
- **必胜提前收手**：某一层已经证明必胜，就不再加深——找到了杀招，
  继续搜纯属浪费（这也是「学习加速」让 AI 变快的一部分）。

### 3.5 七档难度的区别只是"参数"

同一个搜索框架，不同档位只改三个数字：

| 档位 | 搜索深度序列 | 思考时间上限 |
|------|--------------|--------------|
| 入门 | 不搜索（贪心+随机失误） | — |
| 进阶 | 2 层 | — |
| 大师 | 4 层 | — |
| 宗师 | 2→4→6 层 | 2 秒 |
| 棋圣 | 2→4→6→8 层 | 5 秒 |
| 棋仙 | 2→4→…→10 层 | 8 秒 |
| 棋神 | 2→4→…→12 层 | 12 秒 |

所有档位共享一个底线：**一步成五必赢、对方一步成五必堵**——这是代码里
写死的精确判断，不依赖搜索，所以再弱的 AI 也不会犯低级错误。

## 4. UI 界面层：Canvas 画画 + 事件响应

### 4.1 画面是"整幅重画"的

棋盘、棋子、连线、提示圈全部画在一块 Canvas（画布）上。任何变化
（落子、悔棋、回放跳转）都调用 `redraw()` **从头画一遍**：

```
画木纹底 → 画网格线 → 画所有棋子 → 标记最后一手 → 画五连金线 → 画提示圈
```

15×15 的规模全量重绘只需几毫秒，换来的是实现极简单——
不用管理"哪块脏了要重画"。

### 4.2 点击怎么变成坐标

```
屏幕像素 → 减去棋盘留白 → 除以格宽 → 四舍五入 → 最近交叉点
```

`eventCell()` 做的就是这个换算（还处理了页面缩放、手机屏）。

### 4.3 状态面板：一个函数管所有文字

`updatePanel()` 是面板的唯一写入点：状态栏文字、双方名牌、按钮可用/禁用。
它按模式分流（人机 / 双人 / 在线 / 回放 / 观战），每个分支决定"此刻该显示什么"。
**想改任何一处界面文字，都来这个函数找**。

## 5. 存储：浏览器就是你的数据库

项目不用任何数据库，三类数据都存在浏览器的 **localStorage** 里
（浏览器关了数据还在；按"域名+浏览器"隔离）：

| 键 | 存什么 | 什么时候写 |
|----|--------|-----------|
| `gomoku_records_v1` | 对局记录（最近 50 局，供回放） | 每局结束 |
| `gomoku_live_v1` | 当前对局快照（自动续上） | 每次落子/悔棋/重开 |
| `gomoku_opponents_v1` | 对手画像（学习数据） | 每局结束 |

> localStorage 的特点：只能存字符串（所以都要 JSON 序列化）、
> 按域名隔离（127.0.0.1 和局域网 IP 是两个空间）、
> 容量约 5MB（对棋类记录绰绰有余）。

## 6. 在线对战：为什么需要服务器？

两个人在不同电脑上，浏览器之间**不能直接通信**（安全限制），
必须有一个双方都能连上的中间人——服务器。

### 6.1 服务器的两个职责

1. **邮差**：A 落子 → 服务器 → 推送给 B（用 SSE 长连接实时推送）；
2. **裁判**：落子合法性、胜负判定都在服务器上做（复用同一份引擎）——
   两个客户端不可能出现"各自认为自己赢了"的矛盾。

### 6.2 一次在线落子的完整旅程

```
A 点击 (7,7)
   │ POST /api/room/8888/move {token, x:7, y:7}
   ▼
服务器：验证是 A 的回合 → 落子 → 判定胜负 → 组装全量状态
   │ SSE 推送给房间里所有人（A 和 B）
   ├──▶ A 浏览器：重建棋盘，显示 A 的子
   └──▶ B 浏览器：重建棋盘，显示 A 的子，等待 B 落子
```

> 关键设计：服务器每次广播**全量棋盘状态**，客户端收到后整体重建，
> 而不是打补丁——多丢一两个事件也不会导致状态错乱（协议自愈）。

### 6.3 房间、密码、观战

- 房间号就是"频道的名字"：输入相同房间号 = 加入同一频道；
- 密码：首位加入者设定，后来者必须验对（玩家和观战者都验）；
- 满员（2 人）后加入的人自动成为**观战者**：能看棋、不能落子；
  对局席空出来时可以一键转正参战。

## 7. 学习路径建议（如果你想在源码上练手）

按由易到难的顺序读/改：

1. **改文案**：搜 index.html 里的中文提示语，改几处感受页面变化；
2. **改数值**：调 `SC` 分值表里的数字，看 AI 风格怎么变（比如把活三分值翻倍）；
3. **加日志**：在 `chooseAiMove` 里 `console.log` 候选点评分，观察 AI 在"想什么"；
4. **读引擎**：按 `Game → pointScore → genCandidates → negamax → chooseAiMove`
   的顺序读，每个函数都不长；
5. **跑测试**：`node test-engine.mjs`，看断言怎么锁住每一个行为；
6. **改规则**：试着把"连五"改成"连四即胜"（改 `makesFive`/`winLine` 的阈值），
   再跑测试看哪些断言红了——这是理解测试与代码关系的最好练习。

## 8. 初学者常见疑问

**Q: 为什么 AI 计算要放到 Web Worker 里？**
主线程同一时间只能做一件事。12 秒的计算如果放在主线程，页面会完全冻结
（点不动、画不了）。Worker 是浏览器提供的"后台线程"，计算在后台跑，
页面照样流畅。需要打断时 `terminate()` 一键终止。

**Q: localStorage 清了会怎样？**
对局记录、学习画像、自动续上都会重置——相当于"新装"。对局数据本来就在
你自己浏览器里，没有任何云端数据会丢失（在线房间在服务器内存里保留 2 小时）。

**Q: 为什么在线模式的配置要挂载进容器？**
Docker 容器可以理解为一个隔离的小电脑，默认对外面一无所知。
`-v 本机文件:容器文件` 把你的 config.json"递"进容器，服务器才能读到你的端口设置。

**Q: 我改了 index.html，为什么页面没变？**
两种可能：① 浏览器缓存——Ctrl+F5 强制刷新；② 你用 Docker 部署——
页面打包在镜像里，需要 `./gomoku.sh restart`（或重新 build）才会生效。

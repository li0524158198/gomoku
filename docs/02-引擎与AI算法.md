# 02 · 引擎与 AI 算法

本文档描述 `index.html` 中 `/*__ENGINE_START__*/ … /*__ENGINE_END__*/` 之间的纯逻辑引擎：
棋盘表示、胜负判定、棋型评估、搜索框架与七档难度的完整参数。

## 1. 棋盘表示

```js
const SIZE = 15, EMPTY = 0, BLACK = 1, WHITE = 2;
this.b = new Uint8Array(SIZE * SIZE);   // 一维数组，索引 = y*SIZE+x
this.moves = [];                        // [{x, y, c}] 落子序（顺序即回合奇偶）
```

- `at(x, y)`：越界返回 `-1`（把"出界"当作"被堵"，所有边界判断自动统一）。
- `place/undo` 是一对 push/pop，搜索靠"落子-递归-撤销"复用同一个棋盘，零拷贝。
- `moves` 的长度即回合数：`moves.length % 2 === 0 → 轮黑`。UI 与服务器都依赖这一不变量。

### 胜负判定（两个互补函数）

```js
makesFive(x, y, c)   // 虚拟落子：若 c 落在空点 (x,y) 是否成五（沿 4 方向数连子，≥5 即真）
winLine(x, y)        // 实际落子后：返回构成五连（含长连）的全部棋子，按连线顺序排列
```

- `makesFive` 用于**战术预检**（我能不能一步成五 / 对方能不能）与**搜索杀棋延伸**。
- `winLine` 用于**终局裁决与连线高亮**，四方向扫描，双向收集后 `before.reverse()` 拼接，
  保证返回的坐标沿连线单调——UI 画金线就是"首尾连线"，顺序错会画出短一截的线
  （这是第一轮开发中实际踩过的坑，见 06 文档 R1）。
- 长连（六子以上）同样算胜：无禁手规则；`winLine` 返回全部棋子而非恰好五个。
- 平局：`moves.length >= SIZE*SIZE` 且无胜者。

## 2. 棋型评估：pointScore(g, x, y, c)

**含义**：若 c 在空点 (x,y) 落子，该点能产生多大的进攻价值。是整个 AI 的"感官"。

### 2.1 五格滑窗法

对 4 个方向（横、竖、两条斜线），取**所有包含 (x,y) 的 5 格窗口**（共 5 个，offset -4…0）。
把 (x,y) 视为已落子（`t === 0` 直接 `k++`，不读棋盘），统计窗口内：

- `k` = 己方子数（含虚拟落子）
- `z` = 空位数（记录每个空位的位置 t）
- 其余 = 对方子或边界（阻挡）

### 2.2 窗口 → 棋型分类（本评估的核心推导）

**成五**：`k === 5` → 直接返回 `SC.FIVE`（1000 万，早退）。

**四**（`k === 4 && z === 1`）：一子成五。
关键推导：5 格窗口 4 子 1 空，**四子连续 ⟺ 空位在窗口端点**。
- 空位在端点（四子连续，如 `011110` 型）：它是**活四**当且仅当**窗外一侧为空**
  （另一端就是窗口内那个空位，天然为空）。例：`X011110Y`，无论 X 是否被堵，
  只要 Y 空就是活四——因为对手堵一头，我从另一头成五，两点防守防不住。
- 空位在中间（四子有隙，如 `11011` 型）：只有**一个**成五点（那个隙），
  对手一堵即死 → **冲四**（R4）。
- 这个分类只用一次"空位是否在端点 + 窗外一格是否为空"的判断就完成了，
  不需要枚举具体棋型字符串。

**三**（`k === 3 && z === 2`）：试探性填充两个空位之一，
看能否形成上面的"活四"。能 → **活三**（L3）；只能形成冲四 → **眠三**（S3）。
这一递归定义天然覆盖跳三（`011010`、`010110`）：填充间隙后若四子连续且窗外为空即活三。

**二 / 一**（`k === 2 && z === 3`、`k === 1 && z === 4`）：近似计为活二 L2 / 单子 ONE，
不再递归判活（对强度影响小，省两层递归）。

### 2.3 分值表与组合加成

```js
const SC = { FIVE: 10000000, L4: 1000000, R4: 100000, L3: 80000,
             S3: 10000, L2: 6000, S2: 800, ONE: 60 };
```

每方向取**最优**棋型分（dirBest），四方向求和后再叠加组合威胁加成：

| 条件 | 加成 | 含义 |
|------|------|------|
| nL4 ≥ 1 | +400 万 | 已有活四，下一步基本必胜 |
| nL4 ≥ 2 | +800 万 | 双活四 |
| nR4 ≥ 2 | +90 万 | 双冲四（对手只能堵一个） |
| nR4 ≥ 1 且 nL3 ≥ 1 | +90 万 | 四三连接（经典杀型） |
| nL3 ≥ 2 | +50 万 | 双活三 |

> 为什么冲四(10万) > 活三(8万)：冲四强制对手应一手，是"先手"；
> 活三虽也是威胁，但组合价值低于先手四。组合加成的量级（90 万）
> 保证"任何双威胁"都会压过"单个活四以下的所有棋型"。

`evaluate(g, color)` = 双方所有**已落棋子**的 pointScore 之和之差（color 视角）。
同一棋型会被多个棋子重复计数（一个活三的三颗子各计一次），两侧对称、相对量正确，
这是刻意接受的简化。

### 2.4 已知近似与不修的理由

- 无"先手权"（tempo）项：叶子评估不知道轮到谁走。靠搜索深度弥补——
  4 层以上时"我走后你能成什么"都在树内显式展开。
- 活二的判定不看堵位（`11000` 也计 L2）：轻微高估散子价值，让 AI 更愿意发展，
  实测利大于弊。
- 窗口法对"跨窗口的长程组合"（如隔两格的呼应）不敏感：由候选点生成
  （距离 ≤2）与搜索深度共同弥补。

## 3. 候选点生成 genCandidates(g, color, K)

- 范围：已有棋子**切比雪夫距离 ≤2** 内的空点（五子的任何杀着都发生在这个邻域内）。
- 排序分：`pointScore(g,x,y,color) + 0.9 × pointScore(g,x,y,foe)`——
  进攻分 + 打折的防守分。0.9 的含义：同等棋型下"自己做成"略优于"堵死对方"，
  因为堵完后对方还留着先手转换空间。
- 排序取前 K：搜索的剪枝效率完全依赖排序质量，这个静态分就是排序启发。
- 空盘特例返回天元 (7,7)；`findWinPoints`（精确成五点扫描）在 chooseAiMove 层单独处理。

## 4. 搜索框架 negamax

```js
function negamax(g, depth, alpha, beta, color, ext)
```

- **negamax 形式**：节点值恒为"当前行棋方视角"，父层取负。比 min/max 双分支少一半代码。
- **α-β 剪枝**：fail-soft（best 初值 -∞，剪枝后返回当前 best），子窗口 `(-beta, -alpha)`。
- **胜者记谱**：搜索中落子后先查 `winLine`，胜则返回 `WIN_SCORE + depth*1000`——
  depth 是剩余深度，越浅剩得越多，保证"更快获胜"评得更高（AI 不会故意拖长杀局）。
- **节点保险丝 nodeCap**：防止极端局面搜索爆炸（入门~大师 6 万节点封顶）。
- **时间预算 searchDeadline / timedOut**：每 256 个节点查一次钟，超时置位、
  逐层返回 evaluate——供宗师以上档位的迭代加深使用。

### 4.1 杀棋延伸（quiescence，ext 参数）

问题：定深搜索的叶子可能恰好停在"有一方一步成五"的局面上，
静态评估只能看到"四"（约 40 万量级），看不到"下一手就是 1000 万"——
AI 会漏掉自己的杀招、误判攻杀交换。

方案：`depth <= 0` 时先问 `hotFive`——棋面上是否存在任一方的一步成五点。
存在且 `ext > 0` → 不裁剪，`depth = 1; ext--` 继续搜，把这条强制线算到底。

`hotFive` 的关键优化：**成五点必与己方棋子相邻**（五连的Completion点要么贴着连子端部、
要么在间隙里，两侧都是己子），所以只扫每颗棋子**距离 1** 的邻域（约几百次读），
不扫全盘。同时检查双方（攻杀对抗时两方都可能踩到成五点）。

### 4.2 迭代加深 + 时间上限（宗师以上）

```js
for (const d of cfg.depths) {        // 如 [2,4,6,8,10,12]
  逐根候选搜索一遍，记录每个候选的本层分值 vals[]
  if (timedOut) break;               // 本层没搜完 → 沿用上一层结果
  cands.forEach((c,i) => c.val = vals[i]);
  cands.sort((a,b) => b.val - a.val);   // 最优着法排最前 → 加速下一层剪枝（PV 排序）
  best = cands[0];
  if (Date.now() > deadline) break;
}
```

- 时间上限到点后**绝不采纳半截结果**：timedOut 层直接丢弃，用上一完整层。
- 逐层加深本身就是排序启发：上一层的分值排序让下一层的 α-β 剪枝率大幅提高。
- 等价着法随机化：`cands.filter(c => c.val >= bestVal - 1)` 里随机挑一个，
  同分着法轮换，避免 AI 每局开局一模一样。

## 5. AI 主入口 chooseAiMove(g, aiColor, level)

按优先级执行，前面的步骤是**精确的**，不依赖任何评估：

1. **我方一步成五** → 直接下（`findWinPoints`，穷举邻域空点 + `makesFive`，零漏判）。
2. **对方一步成五** → 必堵；多个成五点时选堵完自己 pointScore 最高的（垂死挣扎也挑最优）。
3. 空盘 → 天元；仅一手棋 → 贴身应对（8 邻域第一个空点）。
4. **level 1 入门**：贪心取 genCandidates 前 6 名，60% 取第一、40% 在 2-4 名里随机
   ——刻意制造的"可乘之机"。
5. **level 2 进阶**：定深 2 层搜索，根候选 12。
6. **level 3 大师**：定深 4 层，ext=2（叶子杀棋延伸），根候选 12。
7. **level 4-7**：迭代加深配置表（见 §6），根候选 16/20/24/30，时间上限 2/5/8/12 秒。

任何档位共用第 1、2 步——**这是"准确判断胜负"的底线：再弱的 AI 也不会放过
一步成五，也不会看不见对方的冲四**。档位差异全部体现在"主动进攻的组织能力"上。

## 6. 七档难度配置表

| level | 名称 | 机制 | 深度序列 | 时间上限 | 根候选 K | 杀棋延伸 ext |
|-------|------|------|----------|----------|----------|--------------|
| 1 | 入门 | 贪心+随机 | 1 | — | 6 | 0 |
| 2 | 进阶 | 定深搜索 | 2 | — | 12 | 0 |
| 3 | 大师 | 定深搜索 | 4 | — | 12 | 2 |
| 4 | 宗师 | 迭代加深 | 2→4→6 | 2 秒 | 16 | 8 |
| 5 | 棋圣 | 迭代加深 | 2→4→6→8 | 5 秒 | 20 | 12 |
| 6 | 棋仙 | 迭代加深 | 2→4→6→8→10 | 8 秒 | 24 | 16 |
| 7 | 棋神 | 迭代加深 | 2→4→6→8→10→12 | 12 秒 | 30 | 20 |

配置表是第 8 轮重构的产物（此前宗师/棋圣是 if-else 双写）：
`{ k, t, ext, depths }` 一行一档，加档位只需加一行 + UI 按钮 + 文案数组各一处。

深度与强度的实测关系：每加深 2 层，中盘单手耗时约 ×4（α-β 剪枝后），
时间上限保证"算不完就用浅一层的结果"，这是棋神档单手最慢恰好 ≈12 秒的原因。

## 7. 在线模式的 AI 使用点

- 提示功能：`showHint` 固定按 level=3（大师）计算——提示要"快且不差"，
  与用户选择的难度无关。
- 服务器**不用** AI：在线对局只做人机对弈时的本地 AI；服务器只做规则判定。
  （AI vs AI 的对弈存在于测试压测中，验证引擎稳定性与耗时。）

# 06 · 开发历程 · 逐轮记录

本文档按时间顺序记录九轮交互的完整过程：每轮的需求原文、方案设计、实现要点、
踩过的坑与修复、验证方式。它既是变更史，也是"为什么代码长这样"的决策档案。

---

## R1 · 创建智能五子棋（人机对弈 + 胜负判定）

**需求**：创建一个智能五子棋游戏，让玩家与能够进行策略性落子并准确判断胜负的算法对战。

**决策**：单文件 HTML 交付（双击即玩）；引擎/UI 同文件但以标记分隔（引擎可在 Node 中单测）；
AI 采用"精确战术预检 + 棋型评估 + α-β 搜索"三层结构（详见 02 文档）。

**实现要点**：
- 引擎 `Game` 类 + `pointScore` 五格滑窗评估 + `genCandidates` 邻域候选 +
  `negamax` α-β 搜索；三档难度（入门贪心/进阶 2 层/大师 4 层）。
- 战术地板：任何难度都先穷举"我方一步成五 / 对方一步成五"——AI 的下限由这里保证。
- UI：Canvas 木纹棋盘（种子随机纹理）、径向渐变棋子、落子动画、悬停虚影、
  最后一手标记、WebAudio 合成音效、结算浮层、三档难度切换、执色选择。

**踩坑与修复**：
1. **winLine 顺序错误**：反向收集的连线段用 `unshift(...seg)` 拼接后顺序变成
   `8,7,6,5,9`（非单调），画金线只连了 2 格。修复：`before.reverse()` 后拼接，
   并在测试中加"坐标沿连线单调"断言。
2. **结算浮层遮挡获胜连线**：初版居中 + rgba(.62)+blur(3px)，金线完全看不见。
   两步修复：减淡遮罩 → 把结算卡移到棋盘底部（`align-items: flex-end`）。
3. **「悔棋复盘」按钮名不副实**：最初只关浮层不撤销，改为真正执行 undoMove
   （后来在在线模式又细化为"只关浮层"）。
4. 测试脚本自身两处构造错误（断言点实际能成五；测试局面意外让白棋已有四连——
   AI "不堵反赢"是正确行为），修正测试而非引擎。

**验证**：引擎单测 79 断言通过；大师档单手最慢 110ms；浏览器实测落子/AI 应答/胜负浮层。
（期间发现用户正在应用内浏览器里实时下棋——测试标签页出现了 24 手真实对局，
顺带验证了产品的可玩性；此后所有自动化测试都改用独立标签页。）

## R2 · 双人对战模式

**需求**：增加双人对战功能。

**设计**：`state.mode`（"ai" | "pvp"）+ 对弈模式分段控件；双人模式隐藏"AI 难度"
与"先手选择"两张卡（CSS `body.pvp .ai-only`，后泛化为 `mode-*` 三类）；黑白双方轮流落子。

**实现要点**：
- `humanMove` 分支：pvp 下不触发 AI、按 `currentColor()` 落子；
- 悔棋语义分家：人机撤"AI+玩家"各一手，双人撤最后一手；
- 状态栏/落子记录/名牌全部双口径（黑方/白方）；
- 胜负战报 `🏆 黑棋获胜！/ 🏆 白棋获胜！`。

**验证**：两次真实点击交替落子无 AI 干预；悔棋精确一手；构造四连点击成五出正确战报；
切回人机模式后卡片恢复、AI 正常开局。

## R3 · 对局记录与自动回放

**需求**：可以记录每局的记录，可以自动回放。

**设计**：记录存 localStorage（最近 50 局，字段见 05 文档 §1）；回放采用
**"从空盘重放前 i 手"**的幂等模型而非增量推进——天然支持进度条任意跳转、
单步前进后退、终局重算，无状态漂移。进入回放前拍 `snapshot`，退出时恢复原局面
（进行中的对局或带高亮的终局都原样回来）。

**实现要点**：
- 回放控制条：« ‹ ▶ › » + 进度滑块 + ×1/×2/×4 变速 + 退出；
- 键盘：←/→ 单步、空格播放/暂停；
- 播放中状态栏「▶ 回放中 · 第 i/n 手」、终局「黑棋五连胜 · 共 n 手」；
- 清空记录两段式确认（「确认清空？」2.5 秒自动还原）；
- 回放分支的 updatePanel：按被回放记录的模式显示双方名牌。

**踩坑与修复**：
- 测试断言 `snapshotKept: false` 一度定位为 bug——排查后发现快照里的 8 手棋是
  **用户在同一标签页实时下出来的**（应用内浏览器打开即是可玩页面）。
  教训：共享标签页上的"异常状态"先怀疑人的操作；此后测试一律新开独立标签页。

**验证**：终局自动存档、刷新后记录仍在（localStorage 持久）、回放播到终局重现五连、
单步回退清胜负、退出回放恢复原局面、双人局记录与回放口径、两段式清空。

## R4 · 提示功能

**需求**：增加提示功能。

**设计**：💡 按钮 + H 快捷键；`showHint` 固定按**大师级**引擎计算（提示要"快且不差"，
与用户当前难度无关）；金圈虚线标注 + 状态栏「💡 建议落子 I9」。

**实现要点**：
- 提示计算包一层 `setTimeout(30ms)`：先渲染「正在计算提示…」再同步计算（最深 0.5 秒级）；
- 计算**前后各校验一次**局面（期间可能已重开/进入回话/轮次变化），失效即放弃；
- 失效矩阵：任何落子（含采纳建议）、AI 应答、悔棋、重开、进入/退出回放、终局，
  全部清 `state.hint`；按钮可用态与落子守卫互为镜像。

**验证**：人机模式提示点必为空点且贴棋筋；采纳后消失；H 键有效；回放中/终局禁用；
双人模式黑白双方各自可提示（黑 H8、白 I8 随回合变化）。

## R5 · 在线远程双人对战（房间号匹配）

**需求**：增加在线远程双人对战功能，通过输入房间号匹配。

**设计**：零依赖 Node 服务器（SSE 下行 + POST 上行，见 04 文档）；**服务器权威判定**
——把 index.html 的引擎提取到服务器跑，合法性校验与胜负全在服务器，客户端只展示。
房间号匹配：空位即入（先到执黑），满员 409（R6 改为转观战）。

**实现要点**：
- 客户端第三种模式「在线对战」：房间号输入 + 🎲 随机 + 加入/退出；
- `handleNetMsg` 统一消息入口，每条消息携带**全量房间状态**、客户端整体重建
  （协议自愈，不做增量补丁）；
- 悔棋改为协商制：请求 → 对方同意/拒绝条 → 服务器撤手并广播；
- 重开由任一玩家发起、服务器广播；断线 8 秒宽限 + peek 自检 + 自动清理提示。

**踩坑与修复**（本轮密度最高）：
1. **路由解构错位**：`const [, , , id, action] = parts` 取到 `parts[3]`（action 位）当房间号，
   join 一律 404「房间不存在」。改为 `[, , id, action]`。
2. **改完不重启**：修完解构后测试仍 404——后台进程还跑着旧代码。教训：改服务器必重启。
3. **SSE 全断**：`req.on("close")` 在现代 Node 是"请求体读完"语义（GET 无 body 即立刻触发），
   导致 SSE 建立瞬间 res 就被置空、落子广播全部丢失。用"分段日志"定位到
   `[send] move res? false`，改用 `res.on("close")`（真正连接断开才触发）。
4. **离开后座位不释放**：`detach` 只清 token，座位对象仍为真值，join 判断
   `!r.players[c]` 永远满员。抽象 `hasSeat()`（token 判定）替换所有座位判断。
5. **悔棋后对局未恢复**：同意悔棋只 `game.undo()` 没清 winner/winCells/draw，
   广播出去的 state 仍是终局。补三行清理。
6. **多标签页重复存档**：同浏览器两标签各收一次终局广播、各存一条记录。
   saveRecord 增加内容签名去重（moves 完全相同则跳过）。

**验证**：node 脚本 API 冒烟（加入/满员 409/SSE 读流/九手黑五连/越权与终局落子 400/
悔棋协商/重开）；浏览器双标签 E2E（真实点击同步、双端战报各自视角、悔棋两路径、
重开、退出后座位释放）。引擎回归 87 断言。

## R6 · 观战模式

**需求**：在线对战，房间满的话，可以进入观战。

**设计**：满员 join 自动转观战（`color: 0`，每房间 ≤10 人）；观战者收与玩家相同的
全量广播；落子/悔棋/重开在服务器 403；对局席出现空位时观战界面出现
「有空位了，加入对局」按钮（`takeSeat`），一键接管空出的颜色参战。

**实现要点**：
- `room.spectators: Map<token, {res}>`；`stateOf` 增加 `specCount`；
- 客户端 `state.online.role`（player/spectator）贯通所有守卫：humanMove / ghost /
  showHint / updatePanel（观战分支：黑方 VS 白方名牌、「观战中 · X方行棋」）/
  按钮禁用矩阵 / 终局战报（观战版无存档、无再来一局）；
- takeSeat 后客户端**关闭并重建 SSE**（以玩家身份重新 attach，拿新 init）。

**踩坑与修复**：测试断言两次"失败"实为测试自身错误——B（白）还在局中时白位并未
空出（新人正确转观战）；接管黑位后立刻落子被拒（当时轮白）。服务器行为全部正确。

**验证**：API（满员转观战、计数、广播可达、403 矩阵、takeSeat 后正常落子、离席释放）；
浏览器三标签（观战实时同步、点击无效、空位按钮、接管参战、截图确认 UI）。

## R7 · 新增「宗师」难度

**需求**：增加游戏难度。

**设计**：迭代加深（2→4→6 层，2 秒时间上限）+ **杀棋延伸**（quiescence）+ 根候选加宽到 16。

杀棋延伸的动机：定深搜索的叶子可能停在"有一方一步成五"的局面，静态评估只能看到
"四"（约 40 万），看不到"下一手 1000 万"——AI 会漏杀。方案：叶子处 `hotFive`
检测（双方）任一方向存在成五点则不裁剪、续搜一层（ext 计数封顶）。

**hotFive 的关键优化**：成五点必与己方棋子相邻（端部贴子或两侧贴子），
只扫每颗棋子距离 1 的邻域，成本约为全盘扫描的 1/10。

**踩坑与修复**：测试断言"宗师应封堵对方活三"失败——实际宗师下出了更强的
反先手：发现自己 1 列有 `1.1.1` 骑缝型，先冲四逼白防守、再回防活三。
深度搜索找到了测试作者没想到的正确答案，按更强预期更新断言
（接受封堵两端或冲四反先）。

**验证**：84 断言；宗师单手最慢 2.1 秒（时间上限生效）；大师档因延伸略微变慢但可控。

## R8 · 再增「棋圣 / 棋仙 / 棋神」两档（累计四档高难）

**需求**：再增加难度，宗师级以上的，时间可以放宽一点。（本轮新增棋圣与棋仙、棋神）

**设计**：把宗师/棋圣分支重构为**配置表驱动** `{k, t, ext, depths}`，
之后加档 = 加一行配置 + 一个按钮 + 一句文案：
棋圣 {20, 5s, 12, [2,4,6,8]}、棋仙 {24, 8s, 16, [2,4,6,8,10]}、棋神 {30, 12s, 20, [2,4,6,8,10,12]}。
同时引入 **PV 排序**：每层迭代完成后按本层分值重排候选（最优着法排最前），
显著加速更深一层的 α-β 剪枝（宗师也受益）。

**验证**：84 断言；棋神单手最慢 12.02 秒（12 秒上限精确生效，超时回退上一层结果）；
七档按钮渲染、提示文案、对局记录的难度标注（人机·棋神）均正常。

## R9 · 退出后自动续上

**需求**：增加退出后，自动续上功能。

**设计**：本地局面 + 在线会话双轨持久化（结构见 05 文档 §3）。
每次状态变更全量覆盖写 localStorage；加载时 `tryResume()` 恢复；
在线会话以服务器 `init` 广播为权威重建。

**踩坑与修复**（本轮三个都是真 bug）：
1. **制胜手存档时机错误**：`humanMove` 流程是 `doPlace`（内含 saveLive）→
   `finishCheck`（设置 over/winner）。制胜一手落子时存档的 over 还是 false，
   "已结束局"被当成进行中恢复（刷新后棋盘上明明五连却不判胜）。
   修复：finishCheck 末尾补存；**恢复时增加自洽校验**（重算末手 winLine），
   连历史脏存档都被自动修复。
2. **beforeunload 自动退房与续上互斥**：刷新页面时先触发 beforeunload →
   netLeave 清掉在线会话存档 + 释放座位 → 恢复流程读到的是"已退出"的存档。
   修复：删除该处理器，离开完全交给 SSE 断开 + 8 秒宽限；显式退房仍走按钮。
3. **同浏览器多标签存档竞争**：B 标签页加载会读到 A 的在线会话并以 A 的令牌连接，
   服务器把事件流切给 B、A 被挤下线，且两边存档互相覆盖。修复双管齐下：
   - 服务器：同座位二次 attach 向旧连接发 `replaced` 并关闭，旧窗口
     「该对局已在其他窗口打开」优雅让位；
   - 客户端：saveLive 记录 sessionStorage 标签页指纹，tryResume 仅在指纹匹配
     （同一标签页刷新）时自动续上在线会话，非属主窗口预填房间号、接管存档。

**验证**：人机局恢复（含难度记忆）、AI 回合自动续下（3 手存档刷新后 AI 自动落第 4 手）、
双人局恢复、结束局清空、脏存档自愈、在线刷新续战（座位/执色/棋盘/继续落子全对）、
非属主窗口不抢占 + replaced 让位；引擎回归 83 断言。

## R10 · 房间密码 + 观战上限 5000

**需求**：房间号可以按需设置密码；观察者数量上限提高到 5000。

**设计**：
- **密码**：首位加入者提交的密码即房间密码（创建时确定，后加入者不可更改）；
  之后一切加入（对局席与观战席）都须携带匹配密码，否则 403「房间密码错误」。
  定位是"熟人房间口令"——明文存传、区分大小写、≤16 字符，不承诺安全认证。
- **观战上限**：SPEC_MAX 10 → 5000。纯常量改动，但需要验证服务器的广播循环、
  内存与连接数在 5000 观战（无 SSE 的纯名单）压力下是否正常。

**实现要点**：
- `getRoom(id, pwd)`：仅 join 调用且只在**创建时**落密码；其他端点仍 `rooms.get`
  （密码房不存在时返回 404，不会凭空重建绕过密码）。
- 客户端：在线对战卡新增「房间密码（选填）」输入行；netJoin 携带 pwd、
  成功后禁用输入框；live 存档记录 pwd，刷新续上时自动回填并锁定；
  netLeave / replaced / 会话失效三处恢复输入框。

**踩坑与修复**：
1. **测试环境状态污染**：首轮密码矩阵一半断言"失败"——房间在上一次运行中已存在
   （黑位被占 → 新加入者成了观战者 color 0）。改用 `Date.now` 随机房间号隔离每次测试。
2. **观战者 token 无法 peek（真 bug）**：`peek` 的令牌校验只认对局座位，
   观战者断线自检会 403 → 客户端误报"房间已失效"把观战者踢出。
   修复：peek 返回 `color: isSpec ? 0 : me`。这个 bug 是被压测脚本
   "用观战令牌查 specCount"偶然踩出来的。
3. **压测选型**：5000 次 join 用 `Promise.all` 裸 fetch 会受连接池波动影响，
   改用 `http.Agent({keepAlive: true, maxSockets: 50})` + 50 批 × 100 并发，
   1143ms 跑完零失败。

**验证**：
- 密码矩阵 9 断言全过（创建设密 / 无密码拒 / 大小写敏感 / 正确入座 /
  观战凭密码 / 无密码房直入 / 离席后仍需密码 / 凭密码重进）。
- 观战压测：5000/5000 成功、第 5001 位 409「观战席已满（5000 人）」、零失败。
- 浏览器 E2E：A 设密建房 → B 无密码被拒（提示"房间密码错误"）→ 凭密码执白入座；
  A 刷新（非属主）→ 不抢占、房间号与密码自动回填；B（属主）刷新 → 会话续上、
  密码回填锁定、A 离开后显示等待。

## R11 · 部署能力：一键启动 / 端口范围 / Docker / 云部署

**需求**：打开 index.html 后在线对战要手工运行 node gomoku-server.js，希望自动运行起来；支持 Windows 和 Linux；支持 Docker；支持部署在云服务器；支持配置端口范围。

**关键认知**：浏览器沙箱不允许网页启动进程，「打开 index.html 就自动起服务器」在页面侧无法实现——等价解法是让**启动入口一键化**：
- 服务器启动后自动打开默认浏览器（win32/darwin/linux 三平台分支，`GOMOKU_NO_OPEN=1` 禁用）；
- Windows 双击「启动五子棋.bat」、Linux/macOS 运行 `./start-gomoku.sh`，即完成「起服务器 + 开页面」全部动作；
- 页面切到在线模式时**自动探测**服务器（fetch 探针走 API 路径——静态路径无 CORS 头，file:// 下探测不到），按结果给出「已就绪」或「未检测到，请用启动器」的准确提示。

**端口范围**：启动参数/环境变量支持 `3000`、`3000-3010`（被占用自动顺延）、`3000,8080`（候选列表，最多展开 100 个）；逐个尝试绑定，全不可用时优雅退出并打开首选项地址。新增 `HOST` 环境变量（默认 0.0.0.0，云部署必用）。

**Docker**：提供 Dockerfile（node:20-alpine，仅复制两个文件，内置 GOMOKU_NO_OPEN=1）与 docker-compose.yml（restart: unless-stopped）。容器内无浏览器，禁用自动打开是必须的。

**踩坑与修复**：
1. 页面从存档自动恢复为在线模式时探测不触发、且点击已选中的在线按钮会提前 return——两处都补上 probeServer。
2. Windows 双绑定怪癖：两个进程都能"成功"绑定同一端口，随后才异步报 EADDRINUSE——端口回退逻辑恰好自愈（收到晚到的冲突错误后自动换下一端口），实测最终状态正确。

**踩坑与修复（用户实测反馈）**：Windows 双击「启动五子棋.bat」报错——初版 bat 内含 126 个 UTF-8 中文字符，而 cmd 解析批处理用系统 GBK 代码页，中文被拆成乱码字节，把 if 括号块的闭括号都吞掉直接报语法错误（chcp 65001 救不了解析阶段）。修复：bat 刻意保持纯 ASCII（英文提示），中文提示全部由 Node 进程输出（Windows 上 Node 走宽字符控制台 API，中文不乱码）；Linux 的 start-gomoku.sh 无此问题，保留中文。实测无参/带端口参数两条路径均正常。

**验证**：双实例端口顺延（3000 被占 → 绑 3001）、三实例全占用优雅退出（exit 0）、探测提示两态、服务器无重启持续运行。

## R15 · 停止脚本（配套一键部署）

**需求**：还需要停止脚本。

**实现**：`stop-gomoku.bat` / `stop-gomoku.sh [端口]`，一个脚本同时覆盖两种运行方式：
先 `docker rm -f gomoku`（Docker 部署），再兜底结束仍监听端口的进程（裸 Node / nohup / systemd）。
Linux 兜底链按环境降级：`ss -ltnp` 取 PID（Ubuntu 预装）→ `fuser` → `lsof` → 按进程名
`pkill -f gomoku-server`；Windows 用 `netstat -ano` + `taskkill`。脚本幂等，重复执行不报错。

**踩坑与修复**：bat 末尾的 `timeout /t 2` 在 Git Bash 里调用会撞名 GNU coreutils 的 timeout
（PATH 前置了 /usr/bin）——虽然用户双击场景（System32 的 timeout.exe）不受影响，
仍统一改为 `ping -n N 127.0.0.1 >nul` 的经典延时写法，彻底消除环境差异。

**验证**：Docker 容器停止（容器移除、端口释放）、裸 Node 3010 停止、幂等重复停止、
Git Bash 工具缺失场景优雅降级不报错；停止后 `docker-deploy.sh` 一键恢复部署。

## R16 · 在线执色记忆（退出重进黑白不互换）

**需求（bug 反馈）**：在线对战，退出房间后重新加入，对局中黑白不能互换——现在可以互换。

**根因**：座位按「空位先到先得」分配，令牌每次加入重新签发、与玩家无绑定。
双方都退出后，重进顺序不同（或第三方先加入）就会拿到与之前相反的颜色。

**设计**：服务器按**玩家标识（pid）**记忆每个房间的执色——客户端在 localStorage
生成持久 `gomoku_player_key` 随 join/takeSeat 上报；座位分配优先级：①同 pid 仍在座 →
原色重连（换新令牌，旧的立即失效）；②pid 有执色记忆且座位空闲 → 归还原色；
③自由分配（记忆让位于实际占用）。记忆随房间 2 小时 TTL 回收。

**验证**：API 断言——报告的互换场景（A黑B白双方退出、B先重进）B 仍执白 ✓；
执色被占时让位降级（A 改执白）✓；宽限期内同 pid 重复加入原色换新令牌、旧令牌 403 ✓；
浏览器 E2E（退出重进仍执黑）✓。

**行为说明（刻意设计）**：同一浏览器双标签共享同一 pid，表现为「座位接管」——
后打开的窗口接管座位，先前的窗口收到 replaced 让位。两个真实玩家请使用不同浏览器/设备。

## R20 · git pull 后页面不更新的根因与修复

**需求（bug 反馈）**：Docker 在服务器上 git pull 后执行启动脚本，页面没更新。

**根因**：启动脚本不会重启已在运行的旧实例——旧进程占着端口，新进程按端口占用
逻辑优雅退出（提示可能已在运行），页面继续由旧代码服务。Docker 场景下
docker compose up -d（不带 --build）也会沿用旧镜像。

**修复**：
1. start-gomoku.bat / start-gomoku.sh 启动前先调用 stop-gomoku 停止旧实例
   （启动即重启，git pull 后执行即可生效）；
2. docker-compose.yml 加注释：更新代码须 docker compose up -d --build；
3. README 新增「更新部署」章节；
4. 配置加载增加目录防护：compose 首次挂载不存在的 config.json 会自动创建同名目录，
   启动时检测到目录即移除并重新生成（EISDIR 防护）。

**验证（标记注入法）**：旧实例页面不含标记(0) → 修改 index.html 模拟 git pull →
执行 start-gomoku.sh → 页面含标记(1)；docker-deploy.sh 同样验证通过；
引擎回归 84 断言、页面/配置端点 200。

## 附：贯穿始终的工程习惯

1. **每轮先测后改**：引擎行为变化必跑 `test-engine.mjs`；UI 改动必开浏览器走一遍主流程。
2. **测试失败先怀疑测试**：九轮里有四次"失败"最终证明是测试脚本构造错误或期望过弱
   （R1 两处、R6 两处、R7 反先手），引擎本身无误——但每一次都值得细看，因为
   "AI 下出了测试没想到的好棋"与"AI 有 bug"外观完全相同。
3. **共享标签页是测试大敌**：应用内浏览器页面用户可直接操作，曾两次污染自动化断言；
   独立标签页 + 完成后关闭成为固定流程。
4. **改服务器必重启**：R5 的教训，之后每轮编辑 gomoku-server.js 后都 TaskStop + 重启。
5. **所有计时断言留余量**：高难度 AI 靠时间上限兜底，测试上限 = 上限 + 1 秒。
